# Step 10: Audit solution

**Inputs:** Statement §3.6 (an audit database records **all customer actions**), Step 0 (FR-10, NFR-12, QAS-12 insider tampering, A-09 retention), Step 2 (12-month transaction history schema including IP and OTP used; staff access logs for 12 months; ≥ 10-year KYC/AML retention to verify; synchronized clocks; incident root-cause reports to the SB), Step 4 (Audit service, T2, never blocks T1), Step 8 (MSK, outbox, idempotent consumers), Step 3 (log archive account).

---

## 1. Audit vs application logs vs SIEM

| | **Audit trail** (this step) | Application logs | SIEM |
| --- | --- | --- | --- |
| Question it answers | *Who did what to which data, when, from where, and with what result?* | *Why did the software behave this way?* | *Is someone attacking us right now?* |
| Audience | Compliance, SB, UAFE, legal, customer claims | Engineers, SRE | Security operations |
| Content | Business actions, structured, complete | Free-form, sampled, debug detail | Security events from many sources |
| Integrity | **Immutable, tamper-evident** | Mutable, best effort | Mutable |
| Retention | **12 months online, up to 10 years archive** | Days to weeks | Months |
| Loss allowed? | **No** | Yes | Rarely |

They share the **correlation ID** (Step 14), so an auditor can jump from an audit record to its traces and logs. Audit records are also **fed to the SIEM**, but the SIEM is not the audit store.

## 2. What gets audited

| Source | Examples | Capture mechanism |
| --- | --- | --- |
| **Customer actions (business)** | Transfer ordered / completed / reversed, beneficiary added, limit changed, contact data changed, consent given | **Domain events** via the **transactional outbox** (Step 8) |
| **Customer actions (read)** | Balance viewed, movements queried, detailed data requested from the complementary system, statement downloaded | **API Gateway access records** (every call) + an `@Audited` **interceptor** in the services for reads that need detail (which data was viewed) |
| **Security events** | Login OK / failed, lockout, step-up, device bound / revoked, session ended | Identity provider events + Device service events |
| **Onboarding** | Consent, document and liveness results (scores, no images), registry check, manual review decision | Onboarding service events |
| **Staff access to customer data** (Step 2) | Back-office user viewed a customer, changed a limit, reviewed an onboarding case | Interceptor in back-office APIs: user, system, IP, date, time, **data viewed** |
| **Platform / admin actions** | IAM changes, KMS key use, database admin actions | **CloudTrail** (organization trail) to the **log archive account**; separate from the business audit but under the same immutability rules |

## 4. ADR-015: Audit architecture

**Status:** Proposed

**Context.** Every customer action (writes **and** reads) must be recorded without loss, kept for 12 months online and up to 10 years, protected against insiders (QAS-12), and queryable by compliance. At ~5,000 req/s peak the gateway alone produces tens of millions of records a day.

### Storage options compared

| Option | Immutable (WORM)? | Cost at TB scale | Query | Lifecycle status | Verdict |
| --- | --- | --- | --- | --- | --- |
| **S3 Object Lock (compliance mode)** | **Yes**: nobody, including the root account, can delete or overwrite before retention ends. Assessed for SEC 17a-4 / FINRA / CFTC record-keeping | Lowest, with Glacier tiers | Athena (SQL) | Active | **System of record** |
| DynamoDB | No (mutable) | Medium | Fast key lookups | Active | **Hot index** only |
| OpenSearch | No | High at this volume | Full-text, dashboards | Active | Not needed: SIEM and observability cover search |
| Aurora PostgreSQL + pgAudit | No (a DBA can change rows) | Medium | SQL | Active | Rejected as audit store |
| **Amazon QLDB** | Ledger with cryptographic verification | — | — | **Retired: end of support 31 Jul 2025** | Can't be used |
| Azure Confidential Ledger / Azure SQL ledger | Yes | — | — | Active | Other cloud (ADR-002) |

**Decision.**

1. **Capture:** domain events (outbox) + gateway access records + interceptor records + IdP security events → **Kafka** topics `audit.*` (acks=all, replication factor 3).
2. **Audit service** consumes, validates, normalizes to the schema, **hash-chains**, and writes to:
   - **Immutable archive:** **S3 with Object Lock in compliance mode**, in the separate **log archive account**, as compressed Parquet files partitioned by date and action. Queried with **Athena**.
   - **Hot index:** **DynamoDB** with the last **90 days** of searchable fields (by customer, staff user, correlation ID, transaction number), for the compliance console.
3. **Integrity digests** signed with a KMS asymmetric key every 5 minutes, stored in a second locked bucket (section 5).
4. **Compliance console / API** for authorized staff; every query there is itself audited.

### Justifications

1. **Real immutability, not just permissions.** S3 Object Lock in compliance mode prevents deletion or overwrite by anyone, including administrators and the root user, until the retention date. That's the control QAS-12 needs against insiders, and it has been independently assessed for strict financial record-keeping rules (SEC 17a-4).
2. **No audit event is lost, and the critical path isn't slowed.** Business events come from the **outbox** (written in the same DB transaction as the action, Step 8), so if the action committed, its audit event exists. Delivery is asynchronous through Kafka, so the Audit service (T2) can be slow or down without affecting transfers (T1); it catches up from Kafka.
3. **Cost scales to 10 years.** Parquet compresses audit records ~10×, and S3 lifecycle moves old partitions to Glacier Deep Archive, so a decade of records costs little while staying queryable with Athena.
4. **Tamper evidence on top of immutability.** The hash chain and signed digests prove that no record was removed or changed **before** it reached storage, or in transit, which immutability alone doesn't prove.

### Why not full Event Sourcing

Event sourcing (the event log *is* the system state) gives a natural audit trail, but applied to every service it adds a lot of complexity (rebuilding state, event versioning, snapshots) and the Core, not our services, is the system of record for money. We use the lighter combination: **domain events via outbox + Publish/Subscribe + an append-only audit log**. The Transfer service's state machine history could be event-sourced later if useful.

## 5. Tamper evidence and separation of duties

| Control | How |
| --- | --- |
| **Hash chain** | Each record stores `prevHash` (hash of the previous record in the same Kafka partition) and `hash = SHA-256(prevHash + canonical record)`. Removing or changing one record breaks the chain after it. |
| **Signed digests** | Every 5 minutes the Audit service computes a Merkle root of the new records, **signs** it with a KMS asymmetric key (key usage restricted to the Audit service role) and writes it to a separate locked bucket. |
| **Daily verification job** | Recomputes chains and digests; any mismatch raises a **critical security alert** (QAS-12) to the SIEM. |
| **Separate account** | The archive lives in the **log archive account** (Step 3 landing zone), owned by Security. Application accounts can only **write** (PutObject through a cross-account role), never read, delete or change retention. |
| **SCP guardrails** | Service control policies deny disabling Object Lock, changing bucket policies, or deleting KMS keys used by audit. |
| **Audit the auditors** | Every compliance-console query is itself an audit record (who searched which customer and why: a **case number** is mandatory). |
| **Encryption** | SSE-KMS with a dedicated key; sensitive fields additionally encrypted in the record. |

## 6. Retention and storage tiers

| Records | Retention | Tier |
| --- | --- | --- |
| All customer actions, security events, staff access | **12 months online** (SB minimum), then archive | 0–90 days: DynamoDB hot index + S3 Standard. 90 days–13 months: S3 Standard-IA (Athena). |
| Transactions, KYC / onboarding evidence, AML-relevant records | **10 years** (UAFE, *to verify*) | > 13 months: **Glacier Deep Archive** (restore in hours for investigations) |
| Records under a legal hold (claim, investigation, SB request) | Until released | S3 Object Lock **legal hold** on the affected objects |
| CloudTrail (platform) | 1 year online, 10 years archive | Same pattern |

Object Lock retention is set to the **longest** period that applies to the partition (10 years), since records can't be split later. Records without a 10-year obligation could go to a separate bucket with 13-month retention, lowering storage and the personal-data footprint; decide with Legal.

**LOPDP note:** deletion requests don't apply to records kept to meet a legal obligation (SB, UAFE). Audit records hold IDs and tokens rather than raw personal data where possible, which reduces exposure.

## 8. Component design

```text
 Kong Gateway ─(kafka-log plugin, local buffer)──────┐
 Services ─(outbox: domain events)───────────────────┤
 Services / back office ─(@Audited interceptor)──────┼─► MSK topics audit.* ──► Audit Service (EKS, T2)
 Identity Provider ─(security events)────────────────┘                             │
                                                                                   ├─ Validator / Normalizer (schema, PII tokenization)
                                                                                   ├─ Idempotency filter (auditId)
                                                                                   ├─ Hash Chainer + Digest Signer (KMS)
                                                                                   ├─ Archive Writer ──► S3 Object Lock (log archive account) ──► Athena
                                                                                   ├─ Hot Index Writer ──► DynamoDB (90 days, TTL)
                                                                                   └─ SIEM Forwarder ──► SIEM (Step 12)
 Compliance Console ──► Audit Query API ──► DynamoDB (recent) / Athena (history)   (queries are audited)
 Integrity Verifier (daily job) ──► chains + signed digests ──► alert on mismatch
 CloudTrail (organization trail) ────────────────────────────► S3 Object Lock (log archive account)
```

| Pattern | Where |
| --- | --- |
| **Transactional Outbox** | Services → Kafka (no lost business events) |
| **Publish / Subscribe (Observer)** | Audit is one subscriber among Notification, AML, read models |
| **Interceptor / Decorator (AOP)** | `@Audited` annotation in a shared library, for reads and back-office access |
| **Idempotent consumer** | Duplicate deliveries ignored by `auditId` |
| **Append-only log + hash chain** | Tamper evidence |
| **Pipes and filters** | Validate → tokenize → chain → write |

### Failure handling

| Failure | Behaviour |
| --- | --- |
| Audit service down | Events wait in Kafka (7 days); service catches up. Alert if lag > 5 min. |
| Kafka unavailable | Outbox rows stay in the service DB until Kafka returns; Kong buffers access records on local disk. |
| Malformed record | Sent to `audit.dlq` with an alert; never silently dropped. |
| Region failover | MSK Replicator copies `audit.*` topics to us-east-2; the S3 archive uses **Cross-Region Replication** with Object Lock on the replica. |
